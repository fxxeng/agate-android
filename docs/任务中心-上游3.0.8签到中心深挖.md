## 0. 一句话结论

上游签到中心是**一个页面、三个标签页**（签到中心 / 定时签到 / 签到记录），
外加一个**独立的一级页**「定时任务」。Agate 计划的「六个二级页」是把这两处摊开
重排的结果，其中**三页在上游根本没有对应物**：

| Agate 计划的二级页 | 上游的真实位置 | 结论 |
| :--- | :--- | :--- |
| 福利中心 | 签到中心的「签到中心」tab 里的三块面板 | 不是页面，是 tab 内的分区 |
| 定时签到 | 签到中心的「定时签到」tab | ✅ 真的是独立页 |
| 签到台账 | 签到中心的「签到记录」tab，但**形态已换**（见 §4.3） | 名字要改，内容要换 |
| 保活链 | 「定时签到」tab 里的一块面板（半幅卡） | 不是页面，是页内一块 |
| 周期任务 | **另一个一级页** `data-page="tasks"` | 不是签到中心的子页 |
| 验证码池 | **零 UI**（后台守卫脚本，无挂载点） | 上游没有页面 |

照这六页去铺，会造出三个「进去只有一个开关」的空页面。§5 给出重排建议。

## 1. 上游的页面全集（先确认边界）

`ui/index.html` 里 `data-page` 一共 12 个：

```
accounts  assistant  checkin  docs  gateway  keys
logs      overview   proxies  requests  settings  tasks
```

- **签到中心** = `data-page="checkin"`（`<section class="page" data-page="checkin"></section>`，
  整页由 React 岛 `checkin-page.tsx` 渲染，`ui/app.js` 切页时调 `window.wbCheckinPanel.load()`）。
- **定时任务** = `data-page="tasks"`（React 岛 `tasks-panel.tsx`）。
  文件头明说：「**自动签到曾是本页的一条卡片，已迁到签到中心** —— 签到的执行、范围、
  历史与设置从此只有那一个出处」。所以两者是**平级**关系，不是父子。

签到中心页内三档（`CHECKIN_TAB_OPTIONS`），状态与持久化在 `checkin-state.ts`
（localStorage 键 `workbuddy-desktop-checkin-tab`，脏值回落 `center`）：

| tab | 组件 | 内容 |
| :--- | :--- | :--- |
| `center`（签到中心） | `CenterTab` | 总览卡条 4 格 + 每日签到 + 新手福利 + 活动福利 + 成长任务 |
| `schedule`（定时签到） | `ScheduleTab` | 总开关 + 条目列表（CRUD）+ 保活模型链 |
| `records`（签到记录） | `RecordsTab` | 每账号一行的明细台账（服务端分页 + 筛选） |

Tab 条右端还有一枚**全局徽标**（`id="checkin-badge"`，顶栏状态区镜像它）：
`不可用` / `今日已执行` / `已开启` / `已关闭` 四态。它必须三个 tab 都在 ——
放进某个 tab 里，另两页就丢了镜像。

## 2. 「签到中心」tab

### 2.1 总览卡条（4 格，`ck-stats`）

| 格 | 主读数 | 脚注 | 可点 |
| :--- | :--- | :--- | :--- |
| 今日签到进度 | `todayDone / todayEligible` + Progress 条 | `另有 N 个账号不参与每日签到` / `全部账号均可签到` | — |
| 定时签到 | `启用数 / 条目总数 条启用` | 总开关关：`总开关已关闭 · 在「定时签到」页打开`；开且有下次：`下次 {date} · 点此管理条目`；开但无：`暂无启用的条目 · 点此添加` | ✅ 切 schedule |
| 待领新手福利 | `onboardingUnclaimed 项` | `已有结果 {checked} / 共 {total} 个账号` / `没有支持新手福利的账号` | — |
| 累计签到记录 | `recordTotal` | 固定 `每账号一条明细 · 点此查看「签到记录」` | ✅ 切 records |

`recordTotal` 是**单独一次** `GET /api/checkin-records?limit=1` 拿的（只要 total），
随 `store.version` 重取；拉不到显示 `—` 而不是 0（「拉不到」与「真的是 0」必须分开）。

四格在窄屏（<1080px）落成 2×2。

### 2.2 每日签到面板

- 卡头：标题「每日签到」+ 副标「点击行展开账号明细 · 单账号签到不受范围限制」+
  右上「立即全部签到」（`POST /api/auto-checkin/run`，执行中变「签到中…」）。
- **行为一家一行**，顺序 = `CHECKIN_PROVIDERS` 的注册顺序（12 家：
  `workbuddy, workbuddy-intl, raccoon, autoclaw, autoclaw-intl, qoder, qoder-intl,
  trae, loomy, kuku, officeace, codearts`）。
- 一行里：图标（30×30，无图标回落首字母）+ 名称 + **一句链路说明** +
  右侧 `{total} 账号 · {done} 已签` + 状态徽章 + chevron。
- 状态徽章四档（`groupTone`）：`已签`（全签）/ `部分` / `待签` / `无账号`。
- **没有账号的提供商也占一行**（`无账号` 徽章、不可展开）——
  这样「这家支持签到吗」这个问题不用去别处找答案。
- 展开后是账号明细表：`账号 / 今日签到 / 上次签到时间 / 操作`。
  每行按钮按分组分派：

| 分组 | 按钮 | 说明 |
| :--- | :--- | :--- |
| 其它家（默认） | 一颗：`签到` / `重签`（今日已签时）/ `签到中…` | 走 `checkinAllAccounts(id)` |
| `workbuddy-intl` | **三颗**：`保活` / `领取` / `保活+领取` | 走 `runCheckinActivity(id, mode)` |

`workbuddy-intl` 三颗按钮的判据是**分组 id**，不是账号的 `edition` 字段 ——
Qoder 国际版拆家后同样带 `edition: "intl"`，按 edition 判会把它的账号派去
WorkBuddy 的日活接口，上游稳定 400「该账号不是 WorkBuddy 国际版账号」。
在途键是 `${id}:${mode}`，三颗各自转圈互不牵连（点「保活」不禁用「领取」）。

- `qoder-intl` 分组行**下方常驻一条 UMID 提示**（组件未装时）：说明 + 一键安装，
  `installing` 期间每 3 秒回读一次状态（安装以分钟计，刷新页面不能把「安装中…」永久留住）。

### 2.3 范围外账号的折叠说明

卡底一行灰底说明，把 `outOfScope` 拼成人话：

> `不参与每日签到：{label} ×{count}（{reason}）；…。CodeArts 的一次性奖励在下方
> 「新手福利」，它的每日福利就在上方「每日签到」里；ZCode 的套餐领取见「活动福利」。`

`reason` 由后端给（三种：`国际版账号没有签到活动` / `未接入签到链路` / `没有签到链路`），
界面不自己造理由。

### 2.4 新手福利面板

- 卡头：标题 + 副标「一次性福利 · 签到后自动查询并领取，领完记在本机不再查上游 ·
  点击行展开任务清单」+ 右上「全部查询」（**跳过已结算的账号**）。
- 账号清单由后端 `extras.onboarding` 给（Loomy / 小浣熊 / CodeArts / OfficeAce 四家，
  前端不硬编码家名）。
- 一行：图标 + 账号名 + `已领 {claimed}/{total} · 累计 {earned} 积分` +
  ` · 结算于 {time}`（记忆路径）或 ` · 查询于 {time}`（实查路径）。
  未查过时是 `尚未查询任务状态`。
- 右侧：待领徽章（`{n} 项待领` / `全部领取` / `查询失败`）+「查询任务」+「一键领取（N）」。
  「查询任务」带 `refresh=true` = **强制实查上游**，是唯一的"现在去问一次"入口。
- 展开是逐任务行：勾选圈 + 标题 + `+{points}` + 状态徽章
  （`可领取` / `已领取` / `暂不可领` / `领取中` / 错误原文）。
- **OfficeAce 的特殊性**：它的「一键领取」是**触发今天的结算**（上游按天自动发放，
  待领数恒 0），所以可点性不看"有几项待领"；别家仍是"有待领才可点"。

### 2.5 活动福利面板（ZCode 限时套餐）

- 一行一账号：`今天已领 {n} 份`（本地台账按北京时间判今日）或 `今天未领`。
- 副标：已领 → 「点『套餐明细』看领到了哪几份、什么时候生效；活动期内每天可再领」；
  未领 → 「上次领取 {time} · 领取需通过滑块验证码」或活动说明。
- 按钮始终可点（`去领取` / `套餐明细`）—— **不按"今天领过没"把入口堵死**，
  因为上游是按**套餐**判"已领取"的（领了 A 之后 B 照样能领）。
- **CodeArts 那一行去哪了**：它的每日福利 2026-10 起并入每日签到链
  （`billing::checkin` 的 codearts 分支），所以「活动福利」里撤掉了 CodeArts ——
  同一个账号在两处各挂一个「领」的入口只会让人不确定该点哪个。一次性新人礼仍在「新手福利」。

### 2.6 成长任务面板（WorkBuddy 国内版）

- 行：账号名 + `{total} 项任务 · {pending} 项可完成` + `查询于 {time}`。
- 按钮：`查询任务` / `一键完成` / `领取`。
- 展开四块：
  1. 读数行：`能量 {n} · 连登 {n} 天`（取不到时如实说「本次未取到」）
  2. 任务清单：逐项 `标题 (current/target)` + 状态徽章
     （`已领取` / `可领取` / `可完成` / `未解锁` / `需真实操作` / `暂不支持`）
  3. 猫猫旅行：状态（`在途` / `可领奖` / `可派出` / `今日已派出` / `未领养`）+「巡检一次」
  4. 开学季：`进行中 · 抽奖机会 N 次` / `非活动期` +「执行并抽奖」

## 3. 「定时签到」tab

### 3.1 总开关

`autoCheckin.enabled` = **总开关**，写走老接口 `/api/auto-checkin`（不是
`/api/checkin-schedules`）。关了所有条目都不跑；开着时每条按自己的时刻与范围执行、
各自当天去重。两种状态的说明文案都写在开关右边（`开着：启用的条目按各自时刻执行` /
`关着：所有条目都不执行`）—— 一个开关必须当场说清它管到哪一层。

### 3.2 条目列表

一条目一行：

```
[开关] 展示名（label 空则时刻）  [已停用?]
       每天 {time} · {范围摘要}
       上次执行：{time} · {reason} —— 成功 n · 保活 n · 失败 n
                              [下次 {date}] [立即执行] [编辑] [删除]
```

- **范围摘要**：全选时只说 `全部 {n} 家`（默认就是全选，铺 12 个名字会把「几点」
  和「上次执行」淹掉）；部分勾选才逐家列，全貌在 `title` 里。
- 「下次」只在总开关开 + 本条启用时才有值，否则 `—`。
- 「立即执行」与到点触发**同一条 fire 路径**，后端自带全局防重（在跑时给
  400「签到正在执行中」）。
- 「删除」走自绘确认弹窗（Tauri WebView 里原生 confirm 不弹窗直接放行），
  弹窗里**转义**条目名（名字来自用户输入）。

### 3.3 行内编辑表单

一次只开一张（`editingId`），新建同表单（`editingId = 'new'`）。

- 名称：可选，占位「可选 · 缺省显示时刻」
- 每天时刻：`time` 输入 + 「北京时间 · 错过时点开机后会自动补签」
- 签到范围：复选框网格（`auto-fill minmax(132px)`）+ 全选 / 清空 +
  `到点时逐个签到，已勾 {n} / {total} 家`；勾 0 家时**保存禁用**并红字
  「至少勾一家才能保存（不勾等于这条条目不签到）」
- 底部：取消 / 保存（保存中变「保存中…」）

**新建行必须真渲染出来**，且在列表**首位**（点按钮的地方在卡头右上，离它最近）。
上游为此留了一段教训注释：曾经「添加条目」只把 `editingId` 置成 `'new'` 而没有
任何一处按这个值渲染，点了完全没反应。

### 3.4 保活模型链面板（半幅卡）

WorkBuddy 国际版日活保活用的免费模型，**按顺序逐个尝试、第一个成功即止**。

- 一行一个模型：拖动把手（**唯一**拖动起点，因为行里还有 ×）+ 模型名（等宽）
  + `#{index+1}` 位次 + ×移除
- 顶部：`按序逐个尝试，共 {n} 个` + 「填入缺省链」（仍然要点保存才生效）
- 底部：输入框 + 「添加模型」+ 有未保存的改动提示
- 空清单：「清单为空 —— 保存后恢复缺省链」
- 面板宽度收成 50%（上限 640px）：里面只有一列短清单，拉满整行时灰条会长得没有内容。

**为什么从文本框改成清单**：原先是一个用「、」分隔的输入框，加一个要挪光标、删一个
要精确选中、换顺序得手动剪贴 —— 而这条链的语义恰恰**就是顺序**。

## 4. 「签到记录」tab

### 4.1 形态

每账号一行的**明细台账**（schema v11）。回答的是「到底领到了没、失败错在哪、领了多少」。

- 顶部筛选行：时间档位（今天 / 7 天 / 30 天 / 本月 / 全部，默认**全部**，localStorage 持久化）
  + 结果下拉 + 提供商下拉 + 关键词搜索（失焦 / 回车才提交，Esc 还原）+ 清除筛选 + 条数读数
- 六列：`时间`（含第二行的北京日期）/ `账号` / `提供商` / `来源` / `结果` / `说明`
- 来源五值：`schedule 定时` / `startup 补签` / `manual 手动` / `single 单签` / `activity 活动`
- 结果四值 + 配色：`success 成功领取`（绿）/ `already 今日已领`（蓝）/ `pending 等待窗口`（黄）/
  `failed 失败`（红）；`keptActive` 时另挂一枚「保活」徽章
- 说明列：有 `error` 用红字，否则 `message`（收益文案「今日积分 +100」在这）
- 服务端真分页（offset/limit）+ 页脚分页栏；总数变小导致页码越界时夹回最后一页
- 列设置：显隐 / 顺序（`wbColSettings`）+ 列宽拖动（`table-columns.js`）

### 4.2 清空护栏

与运行日志同一条规则：**带任一筛选 = 只删命中的**；**不带筛选必须显式 `all=1`**
（后端护栏给 400），且前端先过自绘确认弹窗，两条提示语分开说（「清空当前筛选出的」
vs「清空**全部**」）。

### 4.3 ⚠️ 这一页**取代**了原来的「最近签到记录」时间线

`checkin-page.tsx` 文件头写明：

> 原「自动签到设置卡」与「最近签到记录」时间线已迁出：设置长成了多条目（「定时签到」页），
> 记录长成了明细（「签到记录」页），两张总览卡改成入口（点击切页）。

也就是说上游**主动淘汰**了「轮次台账」这种形态（`checkinHistory`，一条一轮、
失败明细前 5 条），换成了每账号明细。Agate 计划的「签到台账」正是被淘汰的那个形态。

内核这边**两套都还在**：
- `core::checkin_history`（轮次汇总，`checkinHistory` 键，`MAX_ENTRIES = 20`，
  带 `{at, date, reason, succeeded, active, total, skipped, failed[≤5], failedCount}`）
- `core::checkin_records`（每账号明细，SQLite 表，带 `{rowId, ts, date, source, reason,
  accountId, accountName, provider, outcome, ok, message, error, keptActive}`）

所以 Agate 应当**以明细为主**（对齐上游现状），轮次只留一个读数（总览卡「累计 N 轮」），
不单独成页。

## 5. 三处与 Agate 计划不一致的地方

### 5.1 验证码池：上游**零 UI**

`ui/zcode-captcha-pool.js` 文件头第一句就是「为什么不做成用户可见的按钮」：

> 转发是后台发生的（用户在别的工具里发请求），没有人会在每条请求前点一次验证。
> 这与「领套餐」的滑块不是一回事：那个是**用户动作**，必须让用户看见、确认；
> 这个是**机器对机器的门禁令牌**。

它是一个每 2.5s 轮询 `GET /api/zcode/captcha` 的后台守卫：`needsTokens` 为真才补货，
`rejected` 变大立刻补一轮，失败只写控制台**不弹 toast**（后台循环弹一次就有第二次）。

页面里没有任何挂载点。v44 设计稿把它画成「任务中心 → 福利」里的一张卡（水位 +
自动铸造开关 + 过码按钮），是 Agate 自己的设计。

**结论**：它唯一值得做成 UI 的部分是**节奏三项**（`target` / `pollMs` / `maxPerRound`）
与**库存读数**（`ready / target / minted / consumed / rejected`）。
一个卡片足够，不值得一个页面。

### 5.2 周期任务：上游是**另一个一级页**

`data-page="tasks"`（`tasks-panel.tsx`），与签到中心平级。六条间隔型任务，
分 `Runner::Backend`（凭证自动维护 / 模型目录刷新 / 软件版本检查）与
`Runner::Frontend`（日志页 / 请求日志页 / 报表页自动刷新）。

关键交互事实：
- `frontend` 那三条的**执行者是页面自己**，所以没有「上次执行 / 下次执行」，
  也**不给「立即执行」按钮** —— 点了也没有任何东西可跑。
- 「软件版本检查」虽同走一组接口，但配置入口收在「更新设置」弹窗里，
  本页**过滤掉**这一行（`HIDDEN_TASK_IDS`），后端定时执行不受影响。
- 间隔输入框在编辑期间由本地草稿接管 value，外部值只在草稿为空时写入 ——
  否则轮询回来的值会把用户敲到一半的内容冲掉。

**结论**：它可以是独立页（上游就是），也可以是任务中心首页的一块卡。
但不能塞进「签到」这条线里 —— 它跟签到没有语义关系。

### 5.3 「签到台账」要改名换内容

见 §4.3。名字建议改成 **「签到记录」**（与上游一致），内容按每账号明细做。

## 7. 建议的页面结构（6 → 4）

按上游真实结构重排，并把「只有一块内容」的页合并：

| # | 页面 | 路由 | 内容 |
| :--- | :--- | :--- | :--- |
| 1 | **签到中心** | 新增 `TASK_CENTER` | 总览 4 格 + 每日签到（分组可展开）+ 新手福利 + 活动福利 + 成长任务 |
| 2 | **定时签到** | `TASK_CHECKIN`（复用） | 总开关 + 条目 CRUD（含行内表单）+ 保活模型链 |
| 3 | **签到记录** | `TASK_HISTORY`（改名） | 明细台账：时间档位 + 三筛选 + 六列 + 真分页 + 清空护栏 |
| 4 | **周期任务** | `TASK_SCHEDULES`（复用） | 六条间隔任务（Backend 可立即执行、Frontend 不可） |

「福利中心」「保活链」「验证码池」三页**取消独立入口**：
- 福利中心 → 已成为页面 1 的三块面板
- 保活链 → 页面 2 里的一块卡
- 验证码池 → 任务中心首页一张读数卡（水位 + 节奏三项设置）

入口位置：任务中心首页仍是分组导航，但五个入口改成四个，
文案从「二级页」变成「分区」，指向更实。

### 为什么不做成六页

三页的实际情况：
- **福利中心**独立成页 = 把页面 1 的三块搬出去，页面 1 只剩总览，而总览的两格
  本来就是「点这里去福利 / 去记录」的入口 —— 会变成"入口指向入口"。
- **保活链**独立成页 = 一个 5 行的清单编辑器独占一屏，而它和「定时签到」是
  同一次配置动作（一个是"几点签"、一个是"用哪些模型保活"）。
- **验证码池**独立成页 = 三个数字输入框 + 一行水位。

手机端一屏能装下的东西，拆成三个页面只多了三次返回。
