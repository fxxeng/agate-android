# 两级内核重构 · 问题审计（P1/P2）

> 审计对象：`fd8b18c..f201624`（21 个提交，两级内核重构 v2.0 P1/P2）
> 依据：`docs/Agate两级内核重构-实施记录.md` + 源码走查（`jni_bridge.rs`、`core/login/*`、`core/providers/*`、`CoreTransport.kt`）
> 结论：架构方向正确（管理面不再依赖端口），但**存在 1 个高危功能缺口 + 3 个中等风险 + 若干低危**。

---

## 0. 一句话结论

「管理面直调」这条链本身是通的（oneshot + 完整中间件栈，鉴权/信封与 HTTP 一致），
**破的是「登录」这条链**——四家靠「网关端口收 OAuth/推送回调」的登录，在 Core 态（网关未运行）下回调落在**没有人监听的端口**上，且**没有前置守卫**，用户会一直等到内核 5 分钟超时。

---

## 1. 高危：四家登录在 Core 态必然失败，且是「静默挂起」
### 证据

`bootstrap` 把**网关端口**写进进程级常量（`core/mod.rs:292-304`）：

```rust
crate::server::core::providers::accio::oauth::set_loopback_port(port);
crate::server::core::providers::codearts::oauth::set_loopback_port(port);
crate::server::core::providers::antigravity::oauth::set_loopback_port(port);
```

`api/session.rs:354`（CatPaw）：

```rust
let callback_base = format!("http://127.0.0.1:{}", state.port);
```

而 Core 态**不 bind 端口**（实施记录 §4：「零端口、零转发」）→ 上述 `redirect_uri` / `callback_base` 指向**关闭的端口**。

`login_start` 里**没有任何 `running()` 守卫**（`grep running() api/session.rs` 无命中）。

### 影响面

| provider | 回调方式 | Core 态（网关未运行） |
|---|---|---|
| `accio` / `accio-cn` | `http://127.0.0.1:<port>/auth/callback-accio` | ❌ 收不到 → 挂起到超时 |
| `codearts` | `http://127.0.0.1:<port>/oauth/callback` | ❌ 同上（有 ticket 轮询兜底，但也要授权码先回落） |
| `antigravity` | `http://localhost:<port>/oauth-callback` | ❌ 同上 |
| `catpaw` | 上游 **POST 推** token 到 `127.0.0.1:<port>/login/catpaw-callback` | ❌ 同上 |
| `trae` | **自己 bind 临时端口**（`callback_server.rs:66` `TcpListener::bind(LOCALHOST, 0)`） | ✅ 正常 |
| 其余（workbuddy/qoder/zcode/cline/officeace/raccoon/kuku/orcaterm…） | 轮询或壳侧拦截 | ✅ 正常 |

### 两个具体缺陷

1. **实施记录 §6 的遗留清单漏了 `catpaw`**——它和 Accio/CodeArts/Antigravity 同属一类，但没被列进「需 UI 明示」。
2. **缺少快速失败**：即使要「不硬解」，也应在 `login_start` 里对这几家先判「端口是否在监听」，未监听直接返回 400「该家需要 loopback 回调，请先运行网关」，而不是让用户等 5 分钟。
   - 注意：`ServerState` **没有** `running()` 方法（字段只有 `port` / `panel_port` / `host` / `local_panel` / `config_dir`）——现成可用的信号是 `jni_bridge.rs` 的 `RUNNING` 静态量，或对 `state.port` 做一次 200ms 的 `TcpStream::connect` 探测。

### 建议（按优先级）

- **P0**：`login_start` 加上述守卫（4 家 + 明确文案）；这是十几行代码的事，收益最大。
- **P0**：客户端按家判断，把这 4 家的「内嵌/浏览器登录」标记为「需先运行网关」，并在按钮上直接给「启动网关」。
- **P1（根治）**：Core 态为登录单独起一个**临时回调监听**（`port=0` 随机），登录结束即释放——Trae 已经是这个范式，可直接复用 `callback_server`。

## 2. 中危：冷启动竞态（Core 未就绪即调用）

`AgateApp.onCreate` 在**后台线程**做 `Gateway.coreInit(...)`，注释明说「失败仅 logcat，UI 轮询 status 兜底」。
而管理面调用不会重试：

- 冷启动后立刻点「添加提供商 / 登录」，`api_call` 取 `CORE` 为 `None` → `{ok:false,error:"core_not_ready"}` → `CoreTransport.Reply.Down` → UI 直接显示失败。
- 现状**没有任何一处对 `core_not_ready` 做等待重试**（`grep -r "core_not_ready" app/src` 无命中）。

**建议**：`CoreTransport.call` 对 `core_not_ready` 做 3~5 次、200ms 间隔的重试（最多 ~1s），仍失败再报错；文案改「内核启动中，请稍后重试」。

---

## 3. 中危：错误文案把内核内部标识直接透给用户

`api_call` 的 `error` 全是英文内部串：`core_not_ready` / `invalid method` / `path must start with /` / `router dispatch failed` / `timeout after 120s`。
`CoreTransport` 原样塞进 `Down.message`，`AccountOps` 等再原样显示。

**建议**：在 `CoreTransport` 里做一层映射（`core_not_ready → 内核启动中`、`timeout after 120s → 操作超时（>2 分钟）`），未命中再兜底原文。

---

## 4. 中危：120 秒同步阻塞 + 不可取消

```rust
match rx.recv_timeout(Duration::from_millis(120_000)) { ... }
```

- JNI 调用线程被**最长阻塞 2 分钟**；超时后已派发的 `oneshot` **无法取消**（继续占用 runtime）。
- 批量余额查询（20 账号并发、各 15~20s 超时）与模型拉取都跑在同一个 runtime 上，worker 紧张时管理面请求会**排队**，容易撞上 120s 上限。

**建议**：区分「快接口」与「慢接口」两档超时（管理面 30s、明确慢接口 120s）；或返回 `pending` + 轮询，避免长阻塞。

---

## 5. 低危：`API_ROUTER` 缓存的是 bootstrap 时的 `state` 快照

```rust
let router = API_ROUTER.get_or_init(|| server::http::router(state));
```

- `state` 是 `CORE.lock()` 里 clone 出来的**首次**快照，含 `port`/`host` 字段。
- 之后 `start_gateway` 用**另一个端口** bind（用户改过端口）时，路由内读到的 `port` 仍是 bootstrap 的值 → `/api/config` 之类展示与实际不符。
- 目前 `Core` 只允许初始化一次（`jni_bridge.rs:210` `if guard.is_some() { return Ok(false) }`），所以**不会**指向失效句柄；但一旦将来支持 Core 重启，这个缓存就是隐患。

**建议**：路由改为每次取 `state` 重建（Router 构造成本低），或把 port 从 `state` 挪到 config 读取。

---

## 6. 低危：请求体无上限

`api_call` 对**响应**设了 4MB（`to_bytes(..., 4*1024*1024)`），但**请求体**无限制。
我们新加的「导入凭证文件」允许 8MB 文件 → base64 后约 11MB 一次性进 JSON → 内存峰值偏高（虽不致命）。

**建议**：客户端把上限降到 4MB（与响应一致），并提示「大文件请用文本 JSON」。

## 7. 确认没问题的部分

- 管理面 9 个数据文件确实都切到了 `CoreTransport`（`AccountOps` / `CustomProviderOps` / `ModelOps` / `TaskOps` / `TaskCenter` / `ScheduledTaskOps` / `LoginClient` / `GatewayRepository` 均 `CoreTransport.configure(apiKey)`）。
- 鉴权与错误信封**与 HTTP 完全同栈**（同一 `router(state)` + 同一中间件），不存在「直调绕过鉴权」。
- `KernelOps.isUp()` 保留 HTTP 是**正确**的（它测的就是端口活性）。
- 实施记录 §3 记录的两个存量 bug（`STARTED` 守卫写反、`status_json` 锁内探活）解法正确。
- 我们此前的提供商改动（通道化 / 自动化卡 / SAF 导入 / 网关探活横幅）在快进后完好，`assembleDebug` 通过。

## 8. 我们这边要改的地方（基于以上）

1. **通道能力按「是否需要网关」再细分**：`accio` / `accio-cn` / `codearts` / `antigravity` / `catpaw` 的 EMBEDDED 与 EXTERNAL 都依赖网关端口 → 网关未运行时这两个通道应置灰并提示「需先运行网关」，而不是让用户点了干等。
2. **新增页横幅口径要精确**：现在写「网关未运行（不影响登录与添加）」，对这 5 家是**不成立**的，应改成按家判断。
3. `CoreTransport` 的 `core_not_ready` 重试 + 文案映射（配合 §2/§3）。

## 9. 深挖：这五家「真的必须网关运行吗」

结论：**是，当前实现下必须**。逐条排除三种「也许能绕过」的假设：

### 假设 1：loopback 端口会不会由别处监听？
不会。`set_loopback_port(port)` 写入的端口与 `start_gateway` 里 `TcpListener::bind` 的**同一个端口**（`state.port`）；Core 态（实施记录 §4「零端口」）没有任何组件监听它。全仓 grep `set_loopback_port` 的调用点只有 `core/mod.rs` 的 bootstrap 一处，没有第二个监听者。

### 假设 2：有没有「拿不到回调也能完成」的兜底？
| provider | 兜底 | 结论 |
|---|---|---|
| `accio` | 无（只认 `authorization_code` 回调） | 必须端口 |
| `antigravity` | 无（Google 授权码 + loopback） | 必须端口 |
| `codearts` | 有 ticket 轮询，但 **ticket 也由登录页回调带回来** | 仍是必须端口 |
| `catpaw` | **反向的**：上游主动 POST token 到我们的 `127.0.0.1:<port>` | 必须有监听者，最刚性 |
| `trae` | 自己 `TcpListener::bind(LOCALHOST, 0)` 起临时端口 | ✅ 不需要网关 |

### 假设 3：用「浏览器登录（EXTERNAL）」能不能绕开？
不能。EXTERNAL 只换「在哪个浏览器打开」，`redirect_uri` / `callback_url` 一个字节都没变 —— 回调仍然打向 `127.0.0.1:<网关端口>`。

### 一个容易误解的点
`state.port` 在 Core 态是「配置上存在、实际没人监听」。所以这些家的登录**不会快速失败**：URL 拼得出来、浏览器也打得开授权页，用户授权完就卡住，直到 `LOGIN_TIMEOUT_MS`（5 分钟）超时。

## 10. 最佳方案（根治）：Core 态为登录临时占用该端口

### 为什么是「临时占用 `state.port`」而不是「另开随机端口」
五家的 redirect 都来自**进程级 `OnceLock<u16>`**（bootstrap 写一次只读）。改成随机端口意味着要把 4 个 `OnceLock` 换成可写（`AtomicU16`）并改所有拼 URL 的地方，牵连面大且引入并发不确定性。
而 Core 态下 `state.port` **本来就空着**（网关没 bind），临时占用它：
- 无需改动任何 URL 拼装逻辑；
- 复用 `server::http::router(state)` —— 鉴权、错误信封、`/oauth/callback`、`/login/catpaw-callback` 全部与网关运行时**完全一致**；
- 登录结束/网关启动前释放，端口归还。

### 落地补丁设计（待 CI 环境执行）

新增 `agate-server/src/server/core/login_listener.rs`：

```rust
//! Core 态登录回调监听器：网关未运行时临时占用 state.port 收 OAuth/推送回调。
static LISTENER: Mutex<Option<(u16, oneshot::Sender<()>)>> = Mutex::new(None);

pub async fn ensure(state: &ServerState) -> Result<(), String> {
    if gateway_running() { return Ok(()); }           // 网关在跑：端口已有监听
    if LISTENER.lock().map(|g| g.is_some()).unwrap_or(false) { return Ok(()); }
    let addr = SocketAddr::new(Ipv4Addr::LOCALHOST.into(), state.port);
    let listener = TcpListener::bind(addr).await
        .map_err(|e| format!("登录需要本机端口 {}，但被占用：{e}", state.port))?;
    let (tx, rx) = oneshot::channel();
    let app = http::router(state.clone());
    spawn(async move {
        let _ = axum::serve(listener, app)
            .with_graceful_shutdown(async { let _ = rx.await; })
            .await;
    });
    *LISTENER.lock().unwrap() = Some((state.port, tx));
    Ok(())
}

pub fn release() { /* 取走 sender 并 send(())，await 优雅关闭 */ }
```

改动点（共 3 处）：

1. `api/session.rs::login_start`：对 `Accio | AccioCn | CodeArts | Antigravity | CatPaw` 先
   `login_listener::ensure(&state).await?`，失败返回 400（文案即上面的「端口被占用」）。
2. `jni_bridge.rs::start_gateway`：bind 之前先 `login_listener::release()` 并等 100ms，避免「自己占着自己」。
3. `login_start` 的任务完成/取消/超时回调里 `release()`（或用空闲 TTL 兜底释放）。

### 当前状态
本机**没有 Rust 工具链与 NDK**（`cargo` 不存在，`jniLibs` 未被 git 跟踪），内核 `.so` 只能由 CI（`.github/workflows/android-build.yml` 第 33-41 行，NDK r27c + cargo-ndk）编译。
因此这轮先落**客户端侧等价修复**（见 §11），上述内核补丁待有 Rust/CI 条件时提交。

## 12. 参考项目对照：`Android-AI-gateway`（作者另一套 Android 实现）

对照源码：`/WorkBuddy/2026-10-13-15-20-55/Android-AI-gateway`

### 12.1 它为什么「不启动网关也能登录」

它有一台**专用于登录回调的临时服务器**（`core/gateway/LoopbackCallbackServer.kt`，NanoHTTPD）：

```kotlin
LoopbackCallbackServer(port, path) { callbackUrl -> ... }   // 绑 127.0.0.1:<专用端口>
```

每家用**各自固定的本地端口**，与网关端口无关：

| provider | 端口 | 路径 |
|---|---|---|
| Trae | 51120 | `/authorize` |
| Antigravity | 51121 | `/oauth-callback` |
| 小浣熊 | 51122 | `/callback` |
| JoyCode | 51123 | `/` |
| OrcaTerm | 51124 | `/orcaterm/callback` |
| CodeArts | 51125 | portal 指定 |
| AutoClaw | 白名单内挑（`portAvailable` 探测） | `/auth/callback-{vendor}` |

生命周期：登录发起时 `startServer()`；**真的收完回调后延迟 1.5s 关闭**；用户长时间不完成则按
`CALLBACK_TIMEOUT_MS` 释放；`port = 0` 时用 `listeningPort` 回填真实端口。

→ 结论：它把「收回调」这件事**与网关解耦**了，所以登录随时可用。这正是我们内核缺的那一层。

### 12.2 它踩过、我们必须避开的坑

1. **CodeArts 是两趟回调**：第一趟带 `secret` + `redirect`，要求 307 跳到 portal 给的地址；第二趟才带 `code`。
   旧实现在第一趟后无条件关端口 → 1.5s 后端口没了 → 第二趟必然失败（表现为「授权后跳回来就报过期」）。
   它用 `REDIRECT_SENTINEL` 标记「这次不是收尾，别关端口」（v2.21.74 修复）。
   **我们内核已实现两趟逻辑**（`core/login/codearts.rs` 处理 `secret/redirect/307` + ticket 轮询），补丁里不要提前释放端口。
2. **AutoClaw 端口白名单**：Zai 按登记的 `redirect_uri` 逐字校验，只能那四个 loopback 端口，需逐个试绑。
3. **根路径归一化**：`/` 与 `""` 比较会导致 404（JoyCode 曾整家登录失败）。
4. **偏好系统浏览器**：它实测部分设备 WebView 渲染异常（整页缩放错乱、输入框文字镜像），所以主用外部浏览器。

### 12.3 四家逐家结论（对照我们内核）

| provider | 参考项目 | 我们内核 | 结论 |
|---|---|---|---|
| **catpaw** | `CatPawLogin`：passport + loopback + **poll-token 兜底** | 同样两条腿赛跑（`core/login/catpaw.rs` 模块头写明，poll 每 1s 问上游） | ✅ **不必须网关**：poll 不经过浏览器，不受 PNA/CORS 影响。已把 `needsGateway` 从 catpaw 摘掉 |
| **codearts** | 51125 + 两趟 307 + ticket 轮询 | 已实现两趟与 ticket 轮询，但回调基址是**网关端口** | ⚠️ 必须网关（Core 态无监听） |
| **antigravity** | 51121（仿官方客户端） | 用网关端口，注释明确「Google desktop client 允许 loopback 任意端口」 | ⚠️ 必须网关；**端口号不是问题**，缺的是监听者 |
| **accio** | **没有登录实现**（`provider/accio` 只有 Protocol/Http/Refresh/Stream，无 `*Login`、未实现 `WebLoginSupport`） | 有完整实现（PKCE + loopback `/auth/callback-accio`） | 所以「accio 没账号未测试」不是遗漏 —— 那项目根本不能登录 accio；我们这边是有实现、缺监听端口 |

### 12.4 因此补丁可以再简化一点

既然参考项目的做法就是「登录期临时起一台回调服务器」，而 Core 态 `state.port` 本来空着，
§10 的方案（临时占用 `state.port` + 复用同一 router）是最小改动版；
如果要更贴近参考项目，也可以固定用 51120~51126 这类专用端口，但那样要改 4 个 `OnceLock`，收益不大。
**唯一必须遵守的**：CodeArts 第二趟回调前不能释放端口。
