# 分支线：生图与图片压缩落地说明（2026-11-20）

> 底座：分支线 `verify/arch-8faa5f5`（`03bb7e4`）。开发分支 `dev`。
> 参照：上游 Agent2API `v3.5.0-beta.3`（`cd0411b`）。
> `main` 全程只读，未做任何改动。

## 1. 为什么先做生图

分支线不是「缺整个功能」，而是**缺一半**：

| 层 | 分支线状态 |
|---|---|
| 能力声明（`providers::images`） | 有：`ImageOperation` / `ImageRequestPlan` / `ImageResponseKind`（OpenAI、WorkBuddy 信封、ModelScope 异步、Gemini SSE 四形态）+ `operation_providers` 三层过滤 |
| 适配器接口（`ProviderAdapter`） | 有：`supports_image_generation` / `supports_image_editing` / `build_image_request` |
| 两家实现 | 有：doubaowork、modelscope |
| **HTTP 入口** | **无** |
| **转发层** | **无** |
| **响应读取层** | **无** |

于是这家的能力在代码里完整存在、却调不到 —— 这是本批要消除的那类「声明了但不可达」。

## 2. 补了什么

### 2.1 内核（Rust）

| 文件 | 职责 |
|---|---|
| `api/images.rs`（624） | 两个入口共用一个 `execute`：校验 → 模型解析 → 转发 → 响应归一 |
| `api/image_input.rs`（493） | multipart / 外链 / data URL 三种上传形态收成同构 JSON |
| `api/image_output.rs`（394） | 响应归一（`b64_json` / 过期签名 URL → 本机字节或短链接） |
| `api/image_assets.rs`（195） | 短链接缓存（128 MiB / 1 小时 TTL），免鉴权（客户端要塞进 `<img src>`） |
| `api/image_compress.rs`（305） | `/api/image-compress` 配置读写 |
| `core/upstream/images.rs`（1043） | 四形态读取：OpenAI / WorkBuddy 信封 / ModelScope 轮询 / Gemini SSE |
| `core/upstream/image_tasks.rs`（57） | ModelScope 异步任务轮询 |
| `core/upstream/image_compress.rs`（729） | 会话图片压缩（白名单只碰 base64 图块，外链 / gif / svg 不动） |
| `core/blocking.rs`（69） | CPU 活让出 worker 的唯一入口（多线程 `block_in_place`，current-thread 就地跑） |

转发层三处改动，每处都有「为什么不能省」：

1. **`ForwardRequest.image` 字段**：生图要走同一条转发链（轮换 / 冷却 / 退避 / 401 / 终止 / 记账）。另开一条链意味着那些行为各有一份实现。
2. **`payload::send_body` 一个入口早退**：五层对话改写（角色归一 / 提示词 / 脱敏 / 压缩 / 原生工具闸门）都以 `messages` 为前提，让它们跑一遍生图请求不是「无操作」，而是有机会把 `prompt` 改坏。
3. **`TransportRequest.payload` 从 `String` 改为 `Bytes`**：参考图编辑走 multipart，直接嵌二进制；`String` 会逼字节做一次「假装是文本」的往返，图会花。

失败语义：`OutboundFailure.stop`。生图的响应读取失败意味着请求**已发出、额度可能已扣**，换号重发等于再扣一次 —— 这类失败直接收尾，不参与顺延。

### 2.2 顺带补的两处小浣熊缺口

生图链路把小浣熊的模型缺陷暴露了出来：

- **`raccoon/headers.rs`（449）**：box_agent 六头 + openai SDK 身份 + 会话关联头。分支的 `build_chat_request` 原本只有 3 个头，缺的正是上游的风控基线 —— 每请求随机的会话 id 配多轮历史会触发**静默丢弃**（不报错、直接不回）。
- **`prepare_chat_body`**：流式 `include_usage`、`max_tokens` 缺省 80000（缺该字段的复杂请求上游会静默不回字节，表现为 10s 首字节超时）、`max_completion_tokens` 翻译、私有字段剥离、GLM 5.3 思考档位归一。

### 2.3 客户端（Kotlin 薄壳）

- `data/ImageOps.kt`（438）：**走 127.0.0.1 + OkHttp，不走 JNI 直调** —— `jni_bridge::api_call` 是全量缓冲（4 MiB / 120 秒），生图响应装不进去。默认 `response_format=url`：内核回一个免鉴权短链接，响应体从几十 MB 降到几百字节。
- `ui/images/ImagesPage.kt`（646）：提示词 / 尺寸档位 / 模型选择 / 参考图编辑 / SAF 保存。
- `ui/components/AgateRemoteImage.kt`（291）：短链接加载态与失败态（过 TTL 只能重新生成）。
- 主题补 `scrim`（深浅两套不透明度不同）。
- 导航：侧栏第一组新增「图像创作」。

### 2.4 清单能力位

`list_item` 原本透传了 `kind`，漏了 `supports_image_generation` / `supports_image_editing` —— 客户端拿到的编辑位恒 `false`，症状是「能生图、但参考图编辑入口不出现」。补上三个键，且只在 `kind == image` 时插入（给对话模型补 `false` 会改变现有 `/v1/models` 的字节）。

## 6. 剩余功能的依赖分析（2026-11-20 实测）

把上游 3.5.0-beta.3 的 api 面逐文件对着分支扫了一遍，结论是：**剩下的不是「若干接口」，而是「若干层地基」**。逐项硬搬会变成大规模改造，风险高于收益。

| 功能 | 卡在哪 | 判定 |
|---|---|---|
| `system_info` / `sidebar_layout` / `panel_events` / `branding` | 硬依赖 `core::cloud_sync`、`update::capabilities`、`config::update_channels`、`plugin_host::provider_settings` | **桌面专属，不做**（Android 没有云同步/更新通道/插件宿主） |
| `zcode_version` / `zcode_claim_verification` | `plugin_host::wasm::verification`（插件 WASM 桥） | 不可移植 |
| `officeace_subscription` | `adapter.admin_action` + `store.account_provider_of`（都要新加 trait 方法） | 暂缓（一家订阅状态，价值低） |
| `model_access` | `request_stats::ApiKeyIdentity` / `RequestSource` / `config::model_key_source`（Key 身份体系） | 暂缓（需先补 Key 身份层） |
| `client_identification` / `reasoning_collapse` | `core/client` 从 69 行的 UA 分类扩成 468 行的可配置识别（catalog + evidence + matcher），且 `reasoning_collapse` 直接读它 | 暂缓（分支已有基础版识别，够用） |
| `prompt_rules` | `core/prompt/rules.rs`（197 行条件匹配引擎）+ payload 提示词层改造 | 暂缓（单提示词已够；按条件匹配是高级用法） |
| `vision_compat` | 537 行配置 + **转发链深度改动**（reroute 要动选路，assist 要额外调一次视觉模型） | **已落地**（本地化重写：raw-only 配置 + API + content/stream 纯函数 + cache/inline 图片内联 + assist/reroute 编排 + 转发链接入 + 客户端 Ops） |
| `runtime_capacity` / `capacity_admission` | 600 行 + 依赖上游协议 crate（`agent2api_provider_protocol`） | 暂缓（Android 单机并发少，默认限流够用） |
| `date_range` / `live_progress` | 只是内部辅助模块（stats_api / pipeline 用），分支的调用方已各自处理 | 不需要 |

**分支已有的等价物**（不算缺）：
- 错误策略：上游的 `error_policy` 是 `retry` / `routing` 那组 legacy 配置的**超集视图**，分支已有后者（重试次数 / 换号次数 / 间隔 / 熔断 / 沉底）。
- 模型清单 / 路由编排 / 签到中心 / 账号批量：分支都已覆盖，且比上游更早。

**结论**（2026-11-20 下午盘点时）：当时真正的功能缺口只剩 `vision_compat`；该缺口现已本地化落地（见 §8.1）。其余要么是桌面管理面，要么是「有基础版但没做高级变体」。

## 7. 地基工程：三层已补（2026-11-20 下午）

上一节说「剩下的不是接口而是地基」。这里记录把地基补掉的三批 —— 判断标准是
**上层接口能否不再写适配代码**，而不是「文件是否搬过来了」。

### 7.1 客户端识别：从固定表扩成两层

| 层 | 入口 | 作用域 |
|---|---|---|
| 严格行为识别 | `client::classify(ua)` | 协议兼容（Codex 推理折叠、按客户端改写）。**不读任何配置** |
| 显示识别 | `client::identify(evidence, settings)` | 统计列、提示词规则匹配 |

这一刀是整套设计的支点：让用户「给客户端改个名字」就改变请求形状，是最难查的
一类 bug。所以配置只影响显示，行为判定永远走固定表。

- `core/client/{catalog,evidence,matcher}.rs`（423 行）：四种匹配（product /
  prefix / contains / exact）；只采集身份头（不碰认证与正文）；同名头重复即判
  畸形（`invalid_headers`）。
- `config/client_identification.rs` 用「懒加载快照 + 写时刷新」，不是每次从 raw
  解析 —— `identify` 每请求都跑，克隆整份配置 Map 不可接受；懒加载也消掉了
  「忘了调 init」这个失效面。
- 三条端点：GET / PUT（整份替换 + revision）/ POST preview（拿「假如收到这些头」
  试跑，并排给 strict 与显示两个结果）。

### 7.2 Key 身份：从「只管能不能进」到「知道是哪一把」

- `request_stats::source`：`ApiKeyIdentity`（id / name / source ∈ key|env|none）
  + `RequestSource`（客户端 + Key + 证据 + 严格行为值）。
- 中间件命中后反查一次记录注入扩展；免鉴权分支显式记 `none`。
  **反查而不改匹配逻辑** —— 那条路径每请求都跑，保持「只比对明文」最省。
- `api_keys::active_entries_from` / `ApiKeyEntry::is_usable`：把「启用的记录」与
  「明文列表」分成两个投影；`is_usable` 额外排除密钥文件丢失后的降级态
  （那种记录的 key 是密文，选中只会换来一次 401）。
- `/api/model-access/models|keys`：与 `/v1/models` 的分工是「探针 vs 权限」——
  前者免鉴权、拿不到限制给全量；这两条必须明确带 Key，不带就 401。
  `x-api-key` 优先于 `Authorization`（显式选择不能被面板凭证兜底替换）。

### 7.3 提示词规则：条件匹配引擎

- `core/prompt/rules.rs`（197 行，自包含）：Field × Operator × Logic。
  **保存时校验、读取时编译**；编译失败不 panic，整块退化成空表并留文案。
  规则**有序**，第一条命中即止（顺序是语义的一部分）。
- 接入只改一处：`ProviderContext::prompt_for(provider_id)` 把「取哪几个维度、
  怎么判」收在上下文里，发送体与降级判断共用同一份决定。
- 规则匹配用**严格行为识别**，不用可配置的显示识别（见 7.1 那条理由）。
- `GET/PUT /api/prompt-rules`：读拆开（两个心智模型，混在一起草稿会互相覆盖）、
  写合写（规则与回落项落在同一组键，修订号必须覆盖四个键）。

### 7.4 仍然待补（按依赖排序）

1. `vision_compat`：已于当日下午本地化落地（assist / reroute 两模式 + 图片内联 + 防递归 + 转发链接入），详见 §8.1；下列两项为低优先级增强。
2. `error_policy`：可达，但它是分支现有 retry/routing 配置的超集视图，默认值
   即当前行为，优先级低于 vision_compat。
3. `runtime_capacity`：600 行 + 上游协议 crate 依赖，需要重写掉那层依赖。
4. 客户端 UI：识别规则页、提示词规则页 —— **已落地**（设置页「智能兼容」/「运维工具」两组入口 + 6 个二级页，详见 §8.2）。

## 8. 全量盘点：上游 api 面 38 个缺失模块的判定（2026-11-20 晚）

按用户要求「彻底处理、不因工作量大否决」，把上游 3.5.0-beta.1 的 **95 个 api 模块**
对着本地 64 个逐文件扫了一遍，38 个缺失模块逐一判定。判据不是「工作量大不大」，而是
**「安卓端有没有这个能力层、以及它是否硬依赖 Android 不存在的子系统」**。

### 8.1 真缺口（应移植，按优先级）

| 模块 | 判定依据 | 状态 |
|---|---|---|
| `accounts_sort` | `save_account_sort` 已实现但**零调用方**；客户端拖拽按本地顺序、没显示已保存排序。纯入口层缺口 | **已落地**（`GET/PUT /api/accounts/sort` + `AccountSortOps`） |
| `vision_compat` | 发图给看不了图的模型时的降级；本地确实缺整条链路 | **已落地**（Phase 1 配置 + API + content/stream 纯函数 + 客户端 Ops；Phase 2 cache/inline 图片内联 + assist/reroute 编排 + `upstream::forward` 接入；本地 cargo check / rustfmt 通过） |
| `reasoning_collapse` | Responses 助手消息补 `phase` 阶段标记；三层地基已齐（严格识别 + responses.rs + raw 配置模式），只差 config key + 标记 + 单开关 API | **已落地**（config key + responses_phase 纯函数 + ResponsesStream/Collector 接线 + `/api/reasoning-collapse` + 客户端 Ops） |
| `maintenance` | 凭证/模型两任务的**执行链已有**（scheduled_tasks.rs），缺执行记录表 + 概览/详情/手动跑/重试入口 | **已落地**（db v22 台账 + `core/maintenance` 记录层 + run_backend 接线 + `GET/POST /api/maintenance` + 客户端 Ops；执行逻辑复用本地，未照搬上游凭证函数） |
| `growth_schedule` | 成长任务定时执行 | **不做**（架构排除）：读上游源码确认硬依赖 `plugin_host::wasm::tasks::travel_state()` + `schedules::definition()`（排程定义在插件侧），正是本仓「不引入插件架构」既定决策要排除的；本地签到排程走 `scheduled_tasks` + `checkin_schedules`，已覆盖用户目标 |
| `accounts_export` | 导出账号为桌面 auth-file 格式 | **已落地**（本地地基 `core/account_transfer` 本就完整，`GET /api/accounts/export` 早已全量导出；本次补 `?id=` / `?provider=` 细粒度导出，单账号分享不必泄露全部 token，空匹配明确报 404；与导入端同一 v2 格式 + customProviders） |
| `assistant_history` / `request_prepare` | 助手编辑历史 + 请求快照回放 | **不做**：硬依赖 `assistant_sessions` 会话持久化 + `model_access::ASSISTANT_TITLE` + `forward_assistant` 整套桌面助手体系，属用户明确要求的「去掉 app 助手部分」；本次编排层（vision_compat）也刻意不引入助手路径 |
| `assistant_images` | 助手页文生图 | **不做**（同上，助手体系）：依赖 `assistant_sessions` / `assistant_images` 附件表（外键随会话删除）/ `PermissionMode` 授权确认，全是桌面助手页概念；本地生图走 `images` 端点 + 客户端 `ImageOps`，已覆盖用户目标 |

**vision Phase 2 本地化取舍**（与上游 3.5.0 的差异）：

- 上游整套依赖桌面地基（`RequestRouting` / `route_context` / `capability` / `RequestTelemetry`
  vision 方法族 / native 协议），本地分支线都没有 ⇒ 用本地已有能力重写同一语义，不照搬。
- 单独调视觉模型 = 独立 `ForwardRequest` + `KeyScope::provider_only` 钉住那一家（与
  `api::model_test::run_forward` 同范式），不改 `ProviderContext`；`ignore_model_gate=true`
  跳过目录开关（用户显式配的目标不该被一个开关挡掉）。
- 图片内联（`core/upstream/vision_compat/inline.rs`）复用 `egress::pinned_address_client`：
  逐地址判公网、DNS 固定防重绑定、逐跳自跟重校验、单图 20MB / 总计 50MB / 最多 4 跳；
  Android 全程在内存，不落盘。识读提示词把图片文字声明为「数据不是指令」防提示注入。
- 防递归 = 内部请求头 `x-agate-vision-internal`，`plan()` 见它就返回 None。
- assist 模式把图片换成识读文字后交回原模型；reroute 模式整体改交给视觉模型并钉住其家。
- 不做 native 协议分支（本地无 native 转发），不做 models.dev / 工具服务联动。

### 8.2 客户端 UI 入口（2026-11-20 晚一并落地）

七个内核能力此前只有 API + 数据层 Ops、App 界面零入口。按「UI 改动先出方案确认」的约定，
用户确认后落地为 **设置页内 1 个就地开关 + 2 个入口分组 + 6 个独立二级页**：

| 落点 | 能力 | 端点 | 界面要点 |
|---|---|---|---|
| 设置「排队与超时」 | reasoning 阶段折叠 | `/api/reasoning-collapse` | 就地 Switch + 乐观置位回弹 |
| 设置「智能兼容」→ 图片兼容 | vision_compat | `/api/vision-compat` | 总开关/未知能力/超时 + 规则启停·模式·目标·复用；整份 PUT 带 revision |
| 设置「智能兼容」→ 客户端识别 | client_identification | `/api/client-identification` | 声明头开关 + 规则启停/字段编辑 + preview 并排 strict/value |
| 设置「智能兼容」→ 提示词规则 | prompt_rules | `/api/prompt-rules` | 规则启停/正文 + fallback；整份 PUT 带 revision |
| 设置「运维工具」→ 账号自动排序 | accounts_sort | `/api/accounts/sort` | 各家规则启停/升降序 + 按家保存/恢复默认 |
| 设置「运维工具」→ 维护记录 | maintenance | `/api/maintenance` | 概览+筛选+详情+手动跑+重试；running 态短轮询回读终态 |
| 设置「运维工具」→ 模型 Key 权限 | model_access | `/api/model-access/*` | 选 Key → 按次传 Key 查询其真实模型权限 |

判据：

### 8.3 桌面专属（有硬证据，不移植）

这不是「工作量大否决」，而是**分支线「不引入插件架构」的既定架构决策**（本地 `core/plugin_host.rs:1,11`
明确写着该文件只是给两个模块补符号的 60 行 shim）：

- **8 个 `plugin_*`**：硬依赖 `core::plugin_host` 的 WASM 宿主 / script runtime / 原生辅助程序本机权限
  授权 / Tauri iframe 页面读取桌面文件系统。Android 端无 WASM 插件宿主、无 Tauri 壳。
- **4 个 `tool_*`（tools / tool_runtime / tool_images / tool_image_results / tool_image_admin）**：硬依赖桌面
  「工具服务」MCP 体系（往本机 AI 客户端配置目录装 Skill/MCP、下载本机桥接脚本、按 panel_port 改写
  base_url）。本地生图走的是同步 `/v1/images/*`（另一条链路），无 MCP 消费者。
- `sidebar_layout`：存在前提是桌面壳 `tauri://localhost` 与网关网页端两个 origin 的 localStorage 隔离；
  本地是单一 Compose 原生应用，无此问题。
- `campaign_rewards` / `officeace_subscription` / `growth_schedule` 的**算法**：在插件侧，网关只透传
  admin_action；本地对应家要么是手动领取（zcode_claim）、要么算法在客户端（kuku/astudio）。
- `zcode_claim_verification`：本地明文放弃的「桌面隐藏验证码窗口 + 插件定时任务」自动领取桥。
