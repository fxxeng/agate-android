## 与方案的偏差

1. **paths.rs 零改动**：方案 §5 说「数据目录由 GatewayConfig.data_dir 注入」，
   实际上游 `paths::config_dir()` 本就有 `AGENT2API_PROXY_HOME` 覆盖口
   （Docker 部署同一机制）。JNI 桥在 bootstrap 前设该环境变量即可，
   比改 paths.rs 更贴合上游设计 → 改动量 -1 文件。
2. **access.rs 内环 adminToken 免登守卫：推迟到 M1**。M0 采用桌面壳同款语义
   （`local_panel = true` + 只听 127.0.0.1 + 无 Key 全放行），loopback 下无
   越权面；`X-Internal-Admin-Token` 守卫与局域网模式（0.0.0.0）一起在 M1 做
   ——但 jni_bridge 的 `admin_token` 参数与打点已预留。
3. **nativeTriggerTask M0 实现 = 转发本机管理 API**（`POST /api/auto-checkin/run`、
   `POST /api/checkin/claim-and-report`，上游 http.rs 已有路由），不直接触达
   业务协程 —— 与面板按钮同一入口，桥层零业务耦合。
4. **qoder_umid / upgrade_api / port_conflict 桩化：M0 未做**。三者不影响
   Android 编译与 M0 验收链路（port_conflict 本就「只描述不动作」；
   upgrade_api 是面板触发的 API；qoder_umid 只在 Qoder 国际版签到时走子进程）。
   首次真机跑通后按需逐个桩。
5. **网卡 MAC 枚举 / machineId 注入：推迟**。上游 device 指纹若在 Android
   上触发受限 API，会在 M1 真机日志里现形，届时再按方案注入。

## 已知风险（记入 M1 验证清单）

- **进程内重启**（stop→start）：内核多处 OnceLock 单例（日志库、全局运行时等）
  按「同数据目录」幂等设计，理论上可重启；但 M0 不把它列为验收项，
  M1 保活链路里专门验证，异常则 Service 改走「杀进程重启」兜底。
- **panic=abort**：.so 内 panic 会带崩宿主 app 进程（与桌面同口径）；
  JNI 层无法 catch，依赖内核「不 panic」的设计承诺（spawn_task 的容错就是为此）。
- **Cargo.lock**：首次 CI 构建后由 workflow 自动提交回仓库（可复现构建）。

## 构建口径（O5）

- 全程 **GitHub Actions**（本地无 Android SDK 的既定纪律；Termux 磁盘仅剩
  6.9G，装不下 Rust 工具链 + target/ ≥3G）。
- 工具链：stable Rust + `aarch64-linux-android` + NDK r27c + cargo-ndk；
  AGP 8.7.3 / Kotlin 2.1.0 / Gradle 8.9 / JDK 17 / compileSdk 35 / minSdk 26。
- 依赖树全纯 Rust TLS 栈（reqwest rustls-tls + webpki-roots）、rusqlite bundled
  （NDK clang 编 sqlite3.c）、ring 0.17（cc 编汇编）——无 openssl/native-tls，
  交叉编译风险集中在这三处，CI 第一轮即验证。
