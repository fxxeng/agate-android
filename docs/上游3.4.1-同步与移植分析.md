## 二、最重要的结论：上游做了一次架构跃迁，本项目不能跟

`docs/plugin-repo-migration.md` 与 `core/providers/mod.rs` 模块头写得很直白：

> 「网关**不包含**任何 provider 实现，只按 git tag 引用它的契约 crate」
> 「各家的转发与账号实现都不在这里 —— 它们整体位于独立的提供商插件」

3.3.0-beta.1 起，上游把**全部 provider 转发、账号、签到、余额**搬进了外部
插件子进程（`core/plugin_host/`，30+ 文件：JSON-RPC 握手、能力申报、崩溃重启、
ed25519 签名校验、包安装/更新）。内核只保留身份、账号库、配置与插件宿主。

直观证据：`core/providers/` 目录从 3.0.8 的 24 家实现，缩到 3.4.1 的 11 个
「只剩地区身份」的模块；`core/login/` 只剩 `lobsterai.rs` 一个文件。

**对 Android 的判断：不移植插件架构。** 理由：

1. Android 不能动态下发并执行未签名原生二进制（应用沙箱 + Play/系统签名校验）；
   插件包是 5 平台各自编译的 `.exe`/ELF，没有 Android target。
2. 插件是**独立子进程 + JSON-RPC 帧管道**，Android 上一个应用起多进程 native
   executable 既不合规也极耗电。
3. 本项目是 **JNI 进程内直调**（`jni_bridge::api_call`），根本不经过 TCP；
   上游 `plugin_host` 的整个握手/租约流在这里没有对应物。
4. 上游 `auth.rs` / `auth_http.rs` / `billing/` 是「provider 搬走后的残卷」，
   对静态编译 provider 的我们是**回退**而不是增强。

所以本项目的「31 家静态编译」路线是对的，要跟的是**插件仓库里那些 provider
的具体实现代码**，把它们继续静态编译进来，而不是跟架构。

## 五、提供商覆盖度：**没有全面对齐**

### 分母必须先说清楚

上游 3.4.1 的 provider id 分布在**三处**，口径不同：

| 来源 | 数量 | 性质 |
|---|---|---|
| 内核 `core/providers/mod.rs::PROVIDERS` | **29** | 旧家的落盘身份契约（已被插件包完全覆盖，是子集） |
| `Agent2Providers/pack.json` | **34** | provider 增强插件，含 `demo`（示例，不启用） |
| `Agent2WebProviders/pack.json` | **4** | 网页插件：`chatglm`、`deepseek-web`、`tabbit`、`tabbit-intl` |
| **三者并集** | **38** | 含 `demo` |
| 减去 `demo` | **37** | 名义 provider |
| 再减去上游自己停用 `qwenwork-intl` | **36** | **真正可添加/调用的分母** |

> `qwenwork-intl` 虽然写在插件 `pack.json` 里，但内核
> `core/providers/availability.rs::SUSPENDED_IDS` 明确把它列为停用：
> 「国际站只接受自己注册的回调地址，本机回环一律被拒；设备码入口整体停用」
> —— 上游自己都加不上账号，所以不该算作缺口。

### 本项目现状

- 内核 `PROVIDERS`：**31** 家
- 客户端 `PresetRegistry.ALL`：**31** 家，与内核**逐条一致**（无多、无缺）
- 31 家**全部**落在上游 3.4.1 的并集里，没有私有/多余 id

### 结论

| 口径 | 数值 |
|---|---|
| 对 3.0.8 时代旧插件包（31 个 id） | **31/31 = 100%**，这个说法今天仍然成立 |
| 对 3.4.1 可添加家（36） | **31/36 ≈ 86%** |
| 对 3.4.1 名义并集（37，含上游停用项） | 31/37 ≈ 84% |

**缺的 5 家可添加 provider：**

| id | 包 | 登录方式 | Android 移植难点 | 建议 |
|---|---|---|---|---|
| `qwenwork` 千问办公国内版 | agent 插件 | 设备授权 PKCE 轮询 | **最小**：复用我们已有的 `qoder/` 模块，只加 `Site::QwenworkCn` 两档 + 客户端身份常量 + 目录条目（约 2-4 文件）。不依赖桌面文件、不需要 WebView | **优先做** |
| `kiro` | agent 插件 | 浏览器 OAuth / 导入 kiro-cli 登录态 / API key | 15 文件 / 5427 行；含 **AWS event stream 二进制帧解析**。但 `local.rs` 强依赖桌面 `%APPDATA%\kiro-cli\data.sqlite3`、Windows 注册表，Android 必须砍掉只留 OAuth/API key | 次优先 |
| `tabbit` / `tabbit-intl` | web 插件 | 国内手机号验证码 / 粘贴 Cookie 或 JWT | 11 文件；HMAC-SHA256 签名 + 签名 key 轮换 + 499 重试；**需要内嵌 WebView 导出 Cookie**；JWT 7 天有效且无 refresh 端点 | 中，但 2 个 id 一起做 |
| `astudio` 讯飞星辰 | agent 插件 | 手机号/密码（极验滑块）/ 粘贴 `modelBearerToken` | 12 文件 / 3499 行；**全靠桌面本机文件 + 注册表**读登录态，滑块登录要内嵌 WebView；OpenAI **Responses** 协议（我们目前只有 chat completions 链） | 最后做，成本最高 |

另外 `qwenwork-intl`（上游自己停用）与 `qwenwork-enterprise`（企业版另立域名）**不建议现在做**。

### ⚠️ 一个必须纠正的老口径

此前记录里「上游 beta 应用清单 51 个 id，我们缺 20 家」的说法，**分母错了**。
3.4.1 的 `desktop-tauri/mobile/src/lib/providers.ts` 现在有 **55 个 ICONS 键**，
但那个文件开头自己就写着「**为什么没有第二份提供商清单**」—— 它只是
**图标文件 + 中文展示名**的映射表，不是实现清单。55 个键里有 **18 个不是 provider**
（精确差集，已用脚本核对）：

- 上游 `availability.rs::SUSPENDED_IDS` 里的停用路线，共 11 个出现在图标表：
  `cursor`、`devin`、`factory`、`zed`、`grok`、`minimax-code`、
  `minimax-code-global`、`qwenwork-enterprise`、`kimi-work`、`opendesign`、
  `nous-portal`（另有 `qwenwork-intl` 虽停用但确有其 provider，不算这里）
- 5 个 `*-subscription` 第三方订阅（独立 FULL-auth 身份，非 provider 实现）
- 2 个图标别名键：`cline`（不是 provider）、`accio-intl`（旧名）

反过来，38 个真实 id 里唯一没有图标的是 `demo`（示例，本就不展示）。
`55 − 18 = 37`，正好等于「名义 provider 37」，两边自洽。

**真实分母是插件 `pack.json` + 内核注册表，不是图标表。** 用图标表当分母会
凭空造出十几家「不存在的缺口」。
